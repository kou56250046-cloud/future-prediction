# requirements — future-prediction

承認日: 2026-09-16 ／ 規模: M ／ 設計の詳細は [design.md](design.md)（承認済みプラン）

## 背景

AI の進化で仕事に求められる技量が変わっている、という実感を、
**当たったか外れたかを測れる形**にしたい。用途は本人のキャリア判断と定点観測であって、
他人への説明資料ではない。

「高精度予測システム」の中身を、このプロジェクトでは次の2点として定義する。

1. 過去から現在までの変化を、感覚ではなく実データの時系列にする
2. 自分の予測を確率つきで登録し、期日に判定し、ベースラインと比べてスコアを出す

2 が中核。ベースライン（現状維持・直線外挿）より良い Brier スコアを出せて初めて
「予測できている」と言える。

## 非目標

**何を作らないかを決めておかないと、実装が際限なく広がる。**

- 一般向けの公開ダッシュボード。本人専用・ローカル完結にする
- 日本市場の求人分析。無料で過去に遡れるデータ源が見つからなかった
- LLM を使った求人票の意味解釈。パーサは正規表現と語彙辞書のみ（無料・オフライン・再現性のため）
- ai-scraping への書き込み。スキーマは向こうの責務、こちらは読み取り専用
- 自動定期実行。手動 `npm run sync` のみ（GitHub Actions cron は公開リポジトリ前提になり、
  キャリア判断のメモを公開する羽目になる）
- **採点される**予測の自動生成。予測を立てるのは人間の仕事で、機械はそれを採点する側にいる。
  採点しない解説文は、執筆者・知識の時点・執筆日・未採点であることを画面に出す場合に限り置く
  （2026-09-17 改定。スキル解説タブの見立て。[guide-and-skill-outlook](../guide-and-skill-outlook/requirements.md)）

## 実装中に判明し、仕様に反映したこと

| 発見 | 対応 |
|---|---|
| フィールドの順序が固定でない求人票が多数（会社\|職種\|勤務地 とも 会社\|雇用形態\|勤務地 ともなる） | 位置ではなく内容で判定するパーサにした |
| `\bengineer\b` が "Engineers" にも "Engineering" にもマッチせず、未分類が34%に | 職種語の語尾を緩めた（3.8% に改善） |
| 2015年前半は勤務形態を書いた求人が3割しかなく、その大半がリモートだったため率が84%になった | 被覆率が閾値未満の期は指標を出さない（`MIN_COVERAGE`）。被覆率自体も指標として残す |
| 指標を upsert にしていたため、定義変更で出力しなくなった値が古いまま残った | 指標ファイルは毎回まるごと書き換える |
| 月次と四半期を同じインデックスに入れていたため、履歴が混ざって外挿が壊れた | `grain` で必ず絞る |
| 最新12期を取ってから過去期で絞っていたため、過去を対象にした予測でベースラインが空になった | `until` を先に渡す |
| `context` に `99999999`（無制限の番兵値）が混ざっており、最大値が 100M になった | 番兵を除外し、`max` ではなく `p95` を使う |
